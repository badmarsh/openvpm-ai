# 🏢 4. Multitenant izolácia (PostgreSQL Row-Level Security)

V modernom veterinárnom cloude, kde na jednej infraštruktúre bežia desiatky nezávislých veterinárnych kliník, je absolútne nepriepustná izolácia dát prvoradou technickou a právnou prioritou.

OpenVPM AI implementuje **dvojvrstvovú architektúru multi-tenant izolácie** na báze databázy PostgreSQL 16 (`docs/security/row-level-security.md`) doplnenú o automatizovaný inicializačný proces a kontinuálny auditný healthcheck.

---

## 1. Dvojvrstvový model ochrany (Defense in Depth)

Bezpečnosť dát sa nespolieha na jediný kontrolný mechanizmus, ale na dve nezávislé bariéry:

### 1.1 Aplikačná vrstva (Application Layer):
* Každá tRPC procedúra a REST endpoint je chránený middleware funkciou `withTenant(db, practiceId, fn)`.
* Táto funkcia automaticky extrahuje `practiceId` z overenej relácie používateľa a nastavuje transakčnú kontextovú premennú v PostgreSQL (`app.current_practice_id`).
* Žiadny bežný klientsky dopyt nemôže manipulovať s parametrom `practiceId`.

### 1.2 Databázová vrstva — Row-Level Security (RLS):
* Aj keby došlo k závažnej chybe v aplikačnom kóde (napr. programátor by zabudol pridať klauzulu `WHERE practice_id = ...`), **databázový server PostgreSQL sám odmietne vrátiť alebo zapísať akýkoľvek riadok patriaci inej klinike**.
* Každá tabuľka s dátami kliniky obsahuje striktnú politiku:

  ```sql
  USING      (app_rls_bypass() OR practice_id = app_current_practice_id())
  WITH CHECK (app_rls_bypass() OR practice_id = app_current_practice_id())
  ```
* Ak nie je v transakcii nastavený platný kontext praxe, premenná je `NULL` a databáza vráti prázdny výsledok (fail-safe default).

## 2. Automatizácia inicializácie RLS (`pnpm db:setup`)

Aby sa predišlo chybám pri nasadzovaní a schema driftu, systém konsoliduje inicializáciu databázy do jediného deterministického príkazu:

```bash
pnpm db:setup
```

Tento príkaz postupne vykonáva:
1. **`pnpm db:bootstrap`:** Inicializácia základnej schémy, tabuliek, indexov a triggerov.
2. **`pnpm db:rls`:** Aplikácia bezpečnostných politík zo súboru `packages/db/rls/enable-rls.sql`. Zapína príznaky `relrowsecurity = true` a `relforcerowsecurity = true` na všetkých multitenant tabuľkách.
3. **`pnpm db:seed:sk`:** Zavedenie overených slovenských demo a referenčných dát (čísla čipov, plemená, očkovacie schémy).

V kontajnerizovanom prostredí (Docker Compose / Dokploy) beží tento proces automaticky v rámci inicializačného kontajnera `db-init`.

---

## 3. Kontinuálny audit a Healthcheck (`/api/health`)

Bezpečnostný stav databázy je nepretržite auditovaný cez endpoint `/api/health`:

* Endpoint vykonáva kontrolu stavu `relrowsecurity` voči katalógu `pg_class` pre všetkých **29 kritických multitenant tabuliek** (pacienti, zdravotné záznamy, klienti, faktúry, lieky, atď.).
* **Okamžité zablokovanie pri chybe:** Ak by na čo i len jedinej tabuľke chýbala aktívna RLS politika, healthcheck okamžite vracia **HTTP 503 Service Unavailable** s chybovou správou:
  `{"ok": false, "error": "29 critical controls missing"}`.
* Load balancer alebo reverzné proxy (Traefik) v takom prípade okamžite odpojí inštanciu zo smerovania prevádzky, čím zabráni akémukoľvek riziku úniku dát.

## 4. Riešenie schema driftu a obnova bezpečnostných politík

V prípade, že počas migrácie alebo údržby dôjde k zrušeniu RLS politík, náprava sa vykoná jednoduchým opätovným aplikovaním skriptu:

```powershell
# Pre lokálne vývojové prostredie:
pnpm db:rls

# Pre vzdialený produkčný server (dev.significa.sk):
Get-Content packages/db/rls/enable-rls.sql -Raw | ssh root@dev.significa.sk "docker exec -i compose-parse-online-port-wdunfq-postgres-1 psql -U openpims -d openpims"
```

---

## 5. Rola s minimálnymi oprávneniami (`openpims_app`)

Pre produkčné nasadenie aplikácia nepristupuje k databáze ako vlastník (`postgres` / `openpims`), ale pod vyhradenou servisnou rolou s najnižšími nutnými oprávneniami:

* Rola `openpims_app` podlieha plnému vynucovaniu RLS politík (`FORCE ROW LEVEL SECURITY`).
* Nemôže vypnúť RLS, meniť štruktúru tabuliek ani manipulovať so systémovými oprávneniami.
* Prístup `withSystem` je striktne vyhradený len pre legitímne medziklinické operácie (napr. prihlásenie používateľa pred identifikáciou kliniky, overenie globálneho API kľúča alebo celoplatformový nočný zálohovací cron).

---

## 6. Testovanie a dôkaz nepriepustnosti

Izolácia je kontinuálne overovaná v CI/CD pipeline prostredníctvom integračného testovacieho balíka:

* **Integračné testy RLS na PostgreSQL 16 (`pnpm db:rls:test`):**
  1. Klinika A nikdy neprečíta záznamy Kliniky B.
  2. Pokus Kliniky A o zápis (INSERT) do dát Kliniky B zlyhá s chybou RLS.
  3. Dopyt bez nastaveného kontextu nevráti žiadne dáta.
  4. Systémový bypass vidí len autorizované systémové záznamy.

> [!IMPORTANT]
> Vďaka dvojvrstvovej architektúre a PostgreSQL Row-Level Security má každý veterinárny lekár 100 % matematickú a kryptografickú záruku, že žiadna iná klinika, konkurenčný lekár ani neoprávnená osoba nemôže získať prístup k jeho pacientom, zdravotným nálezom či ekonomickým výsledkom.
