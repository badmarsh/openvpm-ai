# 🆘 6. Riešenie výpadkov a Disaster Recovery (SLA, RPO/RTO)

Tento dokument popisuje prevádzkové scenáre výpadkov, plán obnovy (Disaster Recovery) a postupy riešenia incidentov na základe dokumentácie `docs/production-readiness/OFFLINE_AND_DISASTER_RECOVERY.md`, `OPERATIONS_RUNBOOK.md` a produkčného manuálu `docs/dokploy-deployment-runbook.md`.

---

## 1. Prevádzkové SLA (Service Level Agreements)

| Metrika | Cieľ |
| :--- | :--- |
| **Dostupnosť platformy** | **99,9 %** mesačne (\~43 min prestoja/mesiac) |
| **RPO (Recovery Point Objective)** | **< 15 minút** — maximálna strata dát pri havárii |
| **RTO (Recovery Time Objective)** | **< 60 minút** — maximálny čas obnovy prevádzky |
| **Reakčná doba P1 (totálny výpadok)** | **< 1 hodina** |
| **Reakčná doba P2 (degradovaná funkčnosť)** | **< 4 hodiny** |
| **Reakčná doba P3/P4 (drobné problémy)** | **< 1 pracovný deň** |

---

## 2. Kroky Disaster Recovery Runbooku

Pri výskyte kritického incidentu (P1) on-call inžinier postupuje podľa tohto protokolu:

| Krok | Akcia | Zodpovedný | Cieľový čas |
| :---: | :--- | :--- | :---: |
| 1 | Detekcia incidentu cez health check (`/api/health`, alerting) | SRE / On-call | < 1 min |
| 2 | Vyhlásenie P1 a aktivácia incidentného protokolu | SRE / Lead Dev | < 5 min |
| 3 | Obnova databázy z poslednej zálohy (PITR, RPO < 15 min) | SRE | < 20 min |
| 4 | Overenie integrity zálohy a RLS politík (`pnpm db:rls`) | SRE | < 10 min |
| 5 | Prepnutie DNS / reverzného proxy Traefik na obnovenú inštanciu | SRE | < 5 min |
| 6 | Smoke test kritických ciest (prihlásenie, SOAP záznam, e-Kasa, MinIO) | QA / Lead Dev | < 10 min |
| 7 | Post-mortem analýza a aktualizácia runbooku | Celý tím | do 48 h |

## 3. Typické prevádzkové incidenty na serveri `dev.significa.sk`

### 3.1 Schema drift / Chýbajúce RLS politiky (HTTP 503 na `/api/health`)
* **Symptóm:** Healthcheck vracia `{"ok": false, "error": "29 critical controls missing"}` a aplikácia odmieta prijímať požiadavky.
* **Príčina:** Po obnove databázy alebo neúplnom behu migrácie neboli aplikované PostgreSQL Row-Level Security politiky (`relrowsecurity = false`).
* **Riešenie:** Spustite aplikáciu RLS bezpečnostných politík:
  ```powershell
  Get-Content packages/db/rls/enable-rls.sql -Raw | ssh root@dev.significa.sk "docker exec -i compose-parse-online-port-wdunfq-postgres-1 psql -U openpims -d openpims"
  ```
  Následne overte, že `/api/health` vracia HTTP 200 s `{"ok": true}`.

### 3.2 Chyba dešifrovania API kľúčov (`Failed to decrypt AI API key`)
* **Symptóm:** V logoch webového kontajnera sa objavujú správy o zlyhaní dešifrovania kľúčov z `ext_ai_settings`.
* **Príčina:** Databáza bola migrovaná alebo obnovená zo zálohy, ktorá bola šifrovaná inou hodnotou `NEXTAUTH_SECRET`, než aká je nastavená na cieľovom serveri.
* **Riešenie:** Aplikácia disponuje vstavanou ochranou proti pádu stránky. Administrátor kliniky jednoducho otvorí `/settings/ai` a zadá platné API kľúče znova, čím sa prešifrujú aktuálnym tajomstvom servera.

### 3.3 Zaseknutý alebo zlyhaný build v Dokploy (Núdzový SSH build)
* **Symptóm:** Dokploy webhook nereaguje alebo build zamrzne v rozhraní Dokploy.
* **Riešenie:** Vykonajte manuálny reštart a rebuild kontajnera priamo cez SSH:
  ```bash
  ssh root@dev.significa.sk "cd /etc/dokploy/compose/compose-parse-online-port-wdunfq/code/ && docker compose build --no-cache web && docker compose up -d --remove-orphans web"
  ```

## 4. Lokálny offline režim ambulancie pri výpadku internetu

Výpadok internetového pripojenia v ambulancii **nezastaví prevádzku**:

* **e-Kasa offline front:** Doklady sa ukladajú lokálne so stavom `OFFLINE_STORED`. Zákonná lehota na spätné odoslanie na portál Finančnej správy SR je **48 hodín**. Po obnovení spojenia prebehne automatická synchronizácia.
* **Lokálna tlač dokladov:** FiskalPRO / Elcom tlačiarne pracujú v lokálnej sieti LAN a vytlačia pokladničný doklad vrátane ochranného kódu PKP aj bez internetu.
* **Núdzové príjmové formuláre:** Pre prípad úplného zlyhania hardvéru sú v ambulancii pripravené tlačiteľné papierové formuláre anamnézy a príjmu. Záznamy sa po obnovení systému spätne zadajú s auditnou poznámkou.

## 5. Kompromitácia tajného kľúča (Secret Breach Protocol)

1. Okamžite rotujte kompromitovaný kľúč (`NEXTAUTH_SECRET`, heslo do PostgreSQL, API kľúče poskytovateľov).
2. Invalidujte všetky aktívne relácie používateľov reštartom webového kontajnera.
3. Kontaktujte zodpovednú osobu (DPO) a vedenie kliniky.
4. V prípade úniku osobných údajov podajte oznámenie Úradu na ochranu osobných údajov SR v zákonnej lehote do **72 hodín** (čl. 33 GDPR).
